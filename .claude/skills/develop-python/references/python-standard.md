# Python engineering standard

Применять эти правила как командный baseline. Сначала учитывать более конкретные AGENTS.md, CLAUDE.md, pyproject.toml, ruff.toml, mypy.ini и pytest.ini текущего репозитория.

## Version and dependencies

- Использовать Python 3.12+.
- Использовать uv для окружения, зависимостей и запуска команд.
- Не вызывать pip, Poetry или Pipenv напрямую.
- Для внутренних пакетов использовать настроенный DevPI. Адрес индекса не хардкодить:
  взять из pyproject.toml проекта, из переменной окружения или из инструкций репозитория.

~~~toml
[[tool.uv.index]]
name = "devpi"
url = "<адрес внутреннего индекса DevPI>"
~~~

- Для локальной разработки внутреннюю библиотеку можно подключить как Git source по SSH или по HTTPS, если это уже принято в проекте. Выбирать тот протокол, который используют остальные зависимости проекта, и не смешивать их в одном файле.
- Перед dev-командами синхронизировать extras командой uv sync --extra dev.
- Не обновлять версии попутно без причины; уважать lock-файл проекта.

## Types and models

- Аннотировать параметры и возвращаемые типы всех функций, включая внутренние.
- Использовать современный синтаксис: list, dict, X | Y вместо List, Dict, Union, Optional.
- Аннотировать вложенные элементы коллекций.
- Для сложных вложенных структур создавать TypedDict, dataclass или Pydantic model; не оставлять dict[str, dict[str, Any]].
- Использовать cast только когда несовпадение типов неизбежно и обосновано.
- Описывать конфигурацию Pydantic-моделями. Секреты получать через Vaulty, а не через поля с открытым значением.

## Design

- Применять SOLID, KISS, DRY и YAGNI по смыслу, не создавать абстракции ради принципа.
- Не мутировать входные аргументы. Возвращать новый объект.
- Если мутация нужна ради памяти или производительности, сделать её явной и вернуть мутированный объект.
- Делать ответственность класса или функции узкой и понятной.
- Предпочитать явные зависимости и простые конструкции.
- Начинать внутренние функции и методы с подчёркивания.

## Imports and naming

- Разделять импорты пустой строкой на стандартную библиотеку, сторонние пакеты и локальные модули.
- Не затенять встроенные имена Python.
- Выбирать доменные имена вместо общих data, obj, tmp, если контекст не очевиден.

## Docstrings

- Добавлять каждой функции минимум однострочный докстринг на русском.
- Для нетривиальной публичной функции использовать Google style с Args, Returns и Raises по необходимости.
- Для короткой приватной функции допустим однострочный докстринг.
- Не дублировать в докстринге очевидную аннотацию; описывать смысл, ограничения и побочные эффекты.

## Logging

- Создавать logger = logging.getLogger(__name__) на уровне модуля.
- Не использовать print внутри функций приложения.
- Использовать параметризованные сообщения logger.info("count=%d", count), а не заранее собранные строки.
- Не логировать токены, пароли, ключи, prompt payload, персональные данные и полный текст чувствительных ответов.
- В Jupyter допускается print в ячейке, но не внутри определений функций. Для объектов использовать явный display().

## Checks

- Использовать Ruff и mypy во всех репозиториях.
- Минимум покрывать функциональность unit-тестами; добавлять интеграционные тесты на границах систем.
- Запускать команды проекта. Если конфигурация не задаёт иное, ориентироваться на:

~~~text
uv run ruff check <package> --fix
uv run ruff format --check .
uv run mypy <package>
uv run pytest -s tests -v --tb=short
uv run pytest --cov=<package> --cov-report=html
~~~

- Не применять --fix во время чистого review без разрешения, поскольку команда меняет файлы.
- Для FastAPI template baseline используется strict mypy, Ruff target py312, complexity 10 и coverage threshold 85%; не переносить эти числа поверх более конкретной конфигурации проекта.

## Review checklist

- Проверить пустые, граничные, ошибочные и конкурентные сценарии.
- Проверить исключения: не теряются ли контекст и traceback, не раскрываются ли внутренние данные.
- Проверить sync I/O в async-коде и освобождение ресурсов.
- Проверить согласованность типов с реальными внешними данными.
- Проверить тесты на изменённый контракт, а не только happy path.
- Отделить автоформатирование от дефектов поведения.
